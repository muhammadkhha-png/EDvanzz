# Performance — Tier 1 (2026-08-31)

Three low-risk backend performance changes. **No frontend/mobile change.** Every runtime change
has a config kill-switch so it can be turned off from Azure App Service settings **without a
redeploy**. Validated end-to-end against SQL Server 2022 in Docker before deploying (see
"How this was validated"). Production is live — these were chosen and tested for zero behaviour
change.

| # | Change | Type | Kill switch (no redeploy) |
|---|--------|------|---------------------------|
| 1 | Response compression (gzip/brotli) | Runtime | `Performance__ResponseCompressionEnabled=false` + Restart |
| 2 | DbContext pooling | Runtime | `Performance__DbContextPoolingEnabled=false` + Restart |
| 3 | ReadyToRun + TieredPGO publish | Build-only | Revert the csproj lines (build-time, no runtime toggle) |

Files touched: `Edvanz.API/Program.cs`, `Edvanz.API/Edvanz.API.csproj`,
`Edvanz.Infrastructure/Persistence/EdvanzDbContext.cs` (OnConfiguring — see #2).

---

## 1. Response compression

**Before:** JSON responses sent uncompressed.
**After:** Responses are gzip/brotli-compressed. The Flutter client already sends
`Accept-Encoding: gzip` and auto-decompresses, so this is transparent — **no app change**.

- **Where:** `Program.cs` — `AddResponseCompression(...)` (services) + `app.UseResponseCompression()`
  placed first in the pipeline. Providers pinned to `CompressionLevel.Fastest` to stay cheap on
  the 1-core B1 (Brotli "Optimal" would peg the CPU). `EnableForHttps = true`.
- **Measured:** the small `/api/Teacher/subjects` payload went 1818 → 748 bytes (**59% smaller**);
  larger list payloads compress ~70–85%.
- **Impact:** faster screen loads, especially on cellular. Biggest *felt* win for the mobile app.
- **Risk:** none to behaviour. Tiny extra CPU per response (negligible at `Fastest`).
- **Security note:** `EnableForHttps` is disabled by default because of BREACH, which targets
  HTML pages that mix a secret (cookie/CSRF token) with attacker-reflected input. This is a
  Bearer-token JSON API with no such reflection, so BREACH does not apply — standard for mobile
  APIs.
- **Kill switch:** `Performance__ResponseCompressionEnabled=false` in App Service → Restart. The
  middleware is only added when the flag is true.

## 2. DbContext pooling

**Before:** `AddDbContext` — a brand-new EF context object is built for every request and thrown
away.
**After:** `AddDbContextPool` — context instances are reused (state reset between requests),
removing per-request allocation and internal-service-provider setup. Real saving on the 1-core B1.

- **Where:** `Program.cs` — the registration branches on the kill-switch and calls a shared
  `ConfigureDbContext` lambda.
- **Required companion change (important):** pooling FORBIDS `OnConfiguring` from modifying
  options — it throws *"'OnConfiguring' cannot be used to modify DbContextOptions when DbContext
  pooling is enabled"* on the first DB query. The old `EdvanzDbContext.OnConfiguring` set
  `ConfigureWarnings(Ignore PendingModelChangesWarning)` and `UseSqlServer(CommandTimeout(300))`.
  Those were **moved into `ConfigureDbContext`** (which feeds both the pooled and non-pooled paths
  and the design-time/migrations context). `OnConfiguring` is now empty (documented in-code).
  - **CommandTimeout is 300** in the lambda on purpose: the old `OnConfiguring`'s 300 was
    overriding the DI block's 30, so 300 was the effective value — kept as-is to avoid changing
    behaviour (a shorter timeout could start failing legitimately long queries).
- **Impact:** less CPU/memory churn and fewer GC pauses per request. Modest but real on one core.
- **Risk:** low, now that OnConfiguring is fixed. The context is otherwise safe to pool
  (options-only ctor, no per-request state, no `SaveChanges` override).
- **Kill switch:** `Performance__DbContextPoolingEnabled=false` in App Service → Restart. The flag
  is read **before** the registration, so it also recovers a boot that ever failed under pooling —
  flip it, restart, and the app falls back to the classic per-request `AddDbContext`.

## 3. ReadyToRun + TieredPGO (publish)

**Before:** the app JIT-compiles more of itself while running and warms up slowly after each
restart.
**After:** `PublishReadyToRun` pre-compiles IL to native at publish time → faster cold start /
fewer slow first requests after a deploy or App Service container swap. `TieredPGO` (already the
.NET 10 default; pinned for documentation) re-JITs hot code for better steady-state throughput.

- **Where:** `Edvanz.API.csproj` PropertyGroup.
- **Impact:** faster startup; small steady-state gain. Steady-state correctness unchanged (tiered
  JIT still re-optimises hot methods).
- **Risk:** none at runtime. R2R is compiled at publish time on the linux-x64 CI runner for the
  linux-x64 self-contained publish; any R2R failure fails the **publish** step and aborts the
  deploy **before** the running app is touched. Verified locally that the R2R publish succeeds
  cleanly (0 errors).
- **Trade-off:** larger published binary (irrelevant on Azure) and slightly longer publish time.
- **Revert:** delete the two csproj lines.

## How this was validated (before deploy)

Booted the real app in Production mode against a fresh SQL Server 2022 container with pooling +
compression ON, and:
- app started cleanly; `GET /health/live` → 200;
- `GET /api/Teacher/subjects` (a real DB read through the pooled context) → **200**, valid JSON,
  20 rows, `Content-Encoding: gzip`;
- 40 sequential requests → **40/40 200** (pool reuse stable, no state leak);
- `dotnet ef migrations has-pending-model-changes` → clean (CI gate still passes after the
  OnConfiguring change);
- `dotnet publish -r linux-x64 --self-contained` with ReadyToRun → succeeded, 0 errors.

The first boot attempt **caught the pooling/OnConfiguring exception** described in #2 — which is
exactly why the app is booted against a live DB, not just built, before deploying.

## Post-deploy prod checks (2 minutes)
1. `GET /health/live` → 200.
2. Any authenticated list endpoint with `Accept-Encoding: gzip` → 200 **and** `Content-Encoding:
   gzip`, body decompresses to valid JSON (proves compression + a pooled DB read work together —
   a pooling regression would 500 here).
3. A search still returns results (e.g. `search=اسامه` finds `أسامة`).

## Full revert
- Runtime, no redeploy: flip the two `Performance__*` App Service settings to `false` + Restart.
- Code: `git revert <commit>` and redeploy — restores `AddDbContext`, removes compression, restores
  the original `OnConfiguring`, and drops the csproj flags.

## Not done here (Tier 2 — deliberately deferred)
- `EnableRetryOnFailure` (left commented in `ConfigureDbContext`): needs the `UnitOfWork`
  transaction boundary wrapped in a DB execution strategy first, or explicit transactions throw.
- In-process (L1) cache in front of the Redis auth snapshot: touches the SecurityStamp revocation
  guarantee; do only with care, or instead co-locate Upstash Redis in the App Service region.
